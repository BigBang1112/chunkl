# Write like BigBang1112

Use this style for project READMEs, technical guides, Q&A, project summaries, and changelogs. Match the purpose and maturity of the target project. Preserve its established terminology and verify every product claim. Style is no reason to invent features, versions, benchmarks, or plans.

## Voice

- Start with what the project does in concrete terms. Name the game, platform, library, or file type when it matters. A short README can stop after a sentence or two if there is little else to explain.
- Write in plain, direct English with technical specificity. Prefer useful facts and cause-and-effect explanations over broad claims or promotional language.
- Do not use semicolons or dashes. Recast the sentence or use a period, comma, colon, hyphen, or parentheses instead.
- Keep the project or tool as the subject in descriptions. Address the reader as "you" for setup steps, choices, and caveats. Use "I" for genuinely personal context or uncertainty. Do not put personal claims in the author's mouth without support.
- Allow a conversational aside, a blunt assessment, or an occasional exclamation when it fits the subject. Keep the main explanation practical and avoid adding personality to every paragraph.
- Be candid about partial support, bugs, workarounds, and future plans. Separate what works now from what is planned or uncertain, and explain the consequence for the reader.
- Use the exact technical names, versions, commands, paths, API identifiers, and game abbreviations that the reader needs. Expand less familiar terms when the audience warrants it. Do not reproduce typos or stale details from the source documents.

## Markdown shape

- Usually open with `# Project Name` and a compact purpose statement. Add only sections the material needs, often `Usage`, `How it works`, `Features`, `Supported games`, `Build`, or a focused warning.
- Use short paragraphs, bullets for features and constraints, numbered steps for a process, code blocks for executable examples, and tables when values genuinely need comparison.
- Put paths, commands, packages, types, and settings in inline code. Use bold for a consequential warning or key requirement rather than decorating ordinary claims.
- Link related projects, dependencies, documentation, and contributors where that context helps readers act or gives credit.
- In changelogs, prefer compact entries with concrete verbs such as "Added", "Fixed", "Updated", or "Renamed", followed by the affected feature or identifier.

Before finishing, check that a reader can tell what the project does, how to use it if applicable, and which limitations matter. Keep a small or unfinished project's documentation small. Do not fill it with generic sections.
